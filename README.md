# autonomy-calc

Калькулятор автономности. Отдельный проект, не связанный с кодом магазина
autonomy.com.ua. Из существующего магазина переносятся только данные и опыт,
не код.

## Текущее состояние: Фаза 0

Реализовано ядро расчёта потребности — чистые функции без внешних зависимостей.

```
core/
  units.py         Вт, Вт·ч, ВА, часы; mah_to_wh
  errors.py        DomainError и потомки
  policy.py        CalculationPolicy — все допущения в одном месте
  appliances.py    ApplianceSpec — тип записи справочника
  load.py          LoadItem, LoadProfile, AutonomyTarget
  requirement.py   EnergyRequirement, LoadContribution, флаги
  demand.py        calculate_requirement()
tests/
  test_architecture.py       ядро импортирует только stdlib
  test_demand_invariants.py  инварианты
  test_golden_scenarios.py   цифры, посчитанные руками
```

Запуск: `pip install -e ".[dev]" && pytest && mypy`

## Не сделано в фазе 0

## ADR-001. Две функции вместо одной

`calculate_requirement` считает потребность на розетке и не знает про батареи.
`evaluate_fit` применяет к ней КПД и глубину разряда конкретного решения.

Цена альтернативы («посчитай мне сразу батарею»): ядро начинает знать про
товары, потребность пересчитывается для каждого кандидата, результат нельзя
показать до подбора и нельзя закэшировать.

## ADR-002. Один одновременный пуск

`пуск = непрерывная мощность + (startup_factor - 1) * мощность худшего мотора`

Сумма всех пусковых токов дала бы требование к инвертору 6 кВт там, где
реально нужен 2 кВт — и убила бы конверсию завышенным чеком. Допущение
возвращается в `assumptions` и показывается пользователю.

## ADR-003. Коэффициента одновременности нет

`diversity_factor = 1.0`. При блэкауте человек включает холодильник, свет и
роутер разом. Ошибка несимметрична: завысил — потерял продажу, занизил —
получил уход в защиту, возврат и отзыв.

## ADR-004. AC и DC считаются раздельно

Повербанк заряжает телефон через USB, инвертора в цепи нет. Общая сумма Вт·ч
дала бы ошибку 10–15 % и не позволила бы одним ядром обслуживать и
повербанки, и станции.

## ADR-005. Пресеты «1..10 часов» — не дело ядра

`AutonomyTarget` принимает любое положительное число часов до 72.
Список кнопок 1,2,…,10 живёт в схеме API (`Literal[1..10]`) и в UI.
Ядро о нём не знает: завтра появится 12 или 24 — правка одной строки в схеме,
тесты домена не трогаются.

## ADR-009. Тариф сети — обязательный параметр без дефолта

`grid_tariff_uah_per_kwh` не имеет значения по умолчанию ни в ядре, ни в UI.
Тариф — не физическая константа, а региональная и коммерческая переменная
(разные области, разные группы потребления, тариф меняется). Подставить
"среднюю по Украине" цифру от имени пользователя — значит выдать чужое
предположение за его расчёт. Пользователь вводит своё значение сам.

## ADR-010. Окупаемость — в кВт·ч, не в месяцах

`payback_energy_kwh`, а не `payback_months`. Причина: у проекта нет
обоснованной цифры "типовое число отключений в месяц" — она разная для
графика 2/2, 4/4 или отдельных аварийных отключений, и любое число было бы
угадыванием. кВт·ч не требует этого допущения: чем больше энергии решение
реально отдаёт, тем ближе окупаемость, независимо от того, произошло это
за неделю или за год. Перевод кВт·ч в месяцы (если понадобится) — задача
слоя каталога, где уже известен профиль использования конкретного клиента.

## ADR-011. Ресурс циклов режется вдвое

`cycle_life_derating = 0.5`. Паспортные 3000 циклов у LiFePO4 получены в
лаборатории: контролируемая температура, ровный разряд, отсутствие глубоких
переразрядов. Реальная эксплуатация — жара в машине, частичные циклы,
периоды простоя — режет ресурс примерно вдвое. Число предварительное и
подлежит уточнению по мере накопления собственной статистики эксплуатации
(как и `declared_capacity_derating` в ADR-006).

## ADR-012. Два независимых числа: LCOE и точка окупаемости

`cost_per_kwh_uah` (LCOE) размазывает капекс на ВЕСЬ паспортный срок службы —
годится для сравнения решений между собой, но для повербанка или станции
почти всегда будет дороже сетевого тарифа: это не ошибка, а честный факт —
резервное питание физически не может быть дешевле стабильной сети.

`payback_energy_kwh` считается по маржинальной стоимости (топливо для
генератора, ноль для накопителя) и отвечает на другой вопрос: после скольких
реально полученных кВт·ч накопленная экономия покроет цену покупки. Для
накопителя это всегда сработает при `grid_tariff > 0` (экономия есть с первого
кВт·ч). Для генератора — не всегда: если топливный опекс дороже тарифа сети,
`payback_energy_kwh = None` и это тоже честный ответ, а не баг.

## ADR-013. Типы топлива — справочник, не домен

`core.economics` не знает про «бензин» и «дизель» — только про голое число
`fuel_rate_l_per_kwh`. Выбор типа топлива с типовым расходом как подсказка —
задача UI/справочника (тот же уровень, что и appliances.yaml из фазы 1):
UI подставляет стартовое значение в поле формы, пользователь может его
поправить под свою модель генератора, и только после этого число уходит в
ядро. Домен от смены линейки типов топлива не должен меняться ни строкой.

Для phase 1 нужно решить (не сейчас): таблица типовых `fuel_rate_l_per_kwh`
по типам топлива — бензин / дизель / газ, вероятно отдельно для инверторных
и обычных генераторов (расход отличается заметно). Цифры — из реальных
паспортов генераторов, которые пойдут в каталог, а не из общих таблиц
интернета: тот же принцип честности, что и с ADR-006 (замеры FNB24P).

## ADR-014. reference — отдельный слой, не адаптер источника

`reference/` — не то же самое, что `adapters/<name>/` из схемы источников
(Rozetka, AliExpress). Это твой собственный курируемый справочник, а не
внешние офферы, которые нормализуются и дедуплицируются. Но правило
направления зависимости то же: `reference` импортирует `core`, `core` о
`reference` не знает. `test_reference_imports_only_core_and_declared_libs`
проверяет это тем же AST-обходом, что и границу `core/`.

## ADR-015. requires_pure_sine — не для всех моторов подряд

Изначально был соблазн поставить `requires_pure_sine: true` на все приборы
с электродвигателем (по правилу "насос ×5-7" из доменных правил). Но
компрессор холодильника с электронной платой управления и универсальный
двигун поверхностного насоса — разный риск: плата может сгореть на
модифицированном синусе, простой насос — просто немного потеряет в КПД.

Флаг стоит там, где цена ошибки — поломка (холодильники, газовый котёл,
CPAP, кисневий концентратор), и снят там, где цена ошибки — просадка
эффективности (насосы, привід воріт). Это предварительная оценка по общей
практике, подлежит уточнению по мере накопления собственных данных —
как и коэффициенты в ADR-006 и ADR-011.

## ADR-016. Starlink и бойлер — несколько записей вместо одной "средней"

Первая версия справочника содержала по одной записи на Starlink и на бойлер
с усреднённой мощностью. Реальные данные показали, что усреднение здесь
не honest-approximation, а потеря критичной информации:

- **Starlink Mini** питается от повербанка с PD напрямую, без інвертора —
  это шина DC_USB, а не AC. Схлопнув Mini и Standard в одну запись на AC,
  калькулятор рекомендовал бы станцію там, где реально хватит повербанка.
- **Бойлер "підтримка t°" vs "повний нагрів"** отличаются на порядок
  (1.5-1.7 кВт·ч/добу против 4-5 кВт·ч за один цикл нагріву). Одна усреднённая
  цифра была бы неправильной в обе стороны в зависимости от сценария.
- **Starlink зимой** (з підігрівом снігу) потребляет вдвое больше — критично
  для зимнего блэкаута, и это ровно тот случай честности, которого нет у
  конкурентов.

Правило на будущее: если у прибора есть режимы или модели, отличающиеся
больше чем на ~30%, — это отдельные записи в справочнике, а не одно
"среднее" число. Усреднение оправдано только когда разброс укладывается
в погрешность самого расчёта (диверсити-фактор, ADR-003).
