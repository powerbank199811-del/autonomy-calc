# autonomy-calc

Калькулятор автономности. Отдельный проект, не связанный с кодом магазина
autonomy.com.ua. Из существующего магазина переносятся только данные и опыт,
не код.

## Текущее состояние: Фаза 0

Реализовано ядро расчёта потребности — чистые функции без внешних зависимостей.

```
core/
  units.py         Вт, Вт·ч, ВА, часы; mah_to_wh
  errors.py        DomainError и потомки
  policy.py        CalculationPolicy — все допущения в одном месте
  appliances.py    ApplianceSpec — тип записи справочника
  load.py          LoadItem, LoadProfile, AutonomyTarget
  requirement.py   EnergyRequirement, LoadContribution, флаги
  demand.py        calculate_requirement()
tests/
  test_architecture.py       ядро импортирует только stdlib
  test_demand_invariants.py  инварианты
  test_golden_scenarios.py   цифры, посчитанные руками
```

Запуск: `pip install -e ".[dev]" && pytest && mypy`

## Не сделано в фазе 0

- `core/solution.py` — SolutionSpec, химия, КПД инвертора, idle_draw
- `core/fit.py` — evaluate_fit(): обратная цепочка потерь, блокеры
- `core/economics.py` — ₴ за кВт·ч и окупаемость
- Справочник приборов в YAML (40–60 позиций) + адаптер загрузки

## ADR-001. Две функции вместо одной

`calculate_requirement` считает потребность на розетке и не знает про батареи.
`evaluate_fit` применяет к ней КПД и глубину разряда конкретного решения.

Цена альтернативы («посчитай мне сразу батарею»): ядро начинает знать про
товары, потребность пересчитывается для каждого кандидата, результат нельзя
показать до подбора и нельзя закэшировать.

## ADR-002. Один одновременный пуск

`пуск = непрерывная мощность + (startup_factor - 1) * мощность худшего мотора`

Сумма всех пусковых токов дала бы требование к инвертору 6 кВт там, где
реально нужен 2 кВт — и убила бы конверсию завышенным чеком. Допущение
возвращается в `assumptions` и показывается пользователю.

## ADR-003. Коэффициента одновременности нет

`diversity_factor = 1.0`. При блэкауте человек включает холодильник, свет и
роутер разом. Ошибка несимметрична: завысил — потерял продажу, занизил —
получил уход в защиту, возврат и отзыв.

## ADR-004. AC и DC считаются раздельно

Повербанк заряжает телефон через USB, инвертора в цепи нет. Общая сумма Вт·ч
дала бы ошибку 10–15 % и не позволила бы одним ядром обслуживать и
повербанки, и станции.

## ADR-005. Пресеты «1..10 часов» — не дело ядра

`AutonomyTarget` принимает любое положительное число часов до 72.
Список кнопок 1,2,…,10 живёт в схеме API (`Literal[1..10]`) и в UI.
Ядро о нём не знает: завтра появится 12 или 24 — правка одной строки в схеме,
тесты домена не трогаются.

## ADR-006. Измеренная ёмкость бьёт заявленную, паспортная режется на 0.85

`_usable_energy` берёт `measured_wh`, если оно есть, и ставит флаг
`USED_MEASURED_CAPACITY`. Если измерения нет — берёт `capacity_wh` и умножает
на `policy.declared_capacity_derating = 0.85`, ставя флаг
`USED_DECLARED_DERATING`. Флаг возвращается наружу, а не глотается внутри.

Производитель указывает ёмкость по ячейкам при номинале 3.7 В. До розетки
доходит меньше: потери в BMS, в преобразовании, саморазряд, самонагрев.
0.85 — предварительная оценка по классу, и она подлежит замене конкретным
числом с FNB24P по мере накопления замеров (как коэффициенты в ADR-011
и ADR-015).

Цена альтернативы «считать по паспорту»: калькулятор систематически завышает
автономность примерно на 15%, человек остаётся без света раньше обещанного —
и это худший из возможных сценариев для проекта, который продаёт доверие.

Цена альтернативы «одно поле `capacity_wh` без разделения»: нечем отличить
позицию, которую ты проверил тестером, от переписанной с карточки продавца.
Разделение «заявлено / измерено» — не украшение карточки, а структурная часть
продукта: без двух полей в типе показать эту разницу физически невозможно.

## ADR-007. Единицы — NewType, а не голый float

`Watt`, `WattHour`, `VoltAmpere`, `Volt`, `Hours` — `NewType` поверх float.
`mah_to_wh` требует напряжение параметром и не имеет варианта «без него».

Самые дорогие ошибки этого домена — размерностные: сложить Вт с Вт·ч,
принять mAh за энергию. Повербанк «20000 mAh» — это 74 Вт·ч, а не 20000
чего-либо; ошибка здесь в 270 раз. `mypy --strict` ловит такое при сборке,
рантайм-оверхед нулевой.

Цена альтернативы «голый float»: ошибка размерности проходит типы, проходит
ревью и всплывает уже цифрой на экране пользователя.
Цена альтернативы «полноценные value-объекты с `__add__`»: рантайм-оверхед
и шум в каждой формуле ради проверки, которую `NewType` даёт бесплатно.

## ADR-008. Округление — один раз, на выходе ядра

Внутри `evaluate_fit` и `calculate_ownership_cost` всё считается во float.
`round_energy` / `round_power` вызываются только при сборке итогового
`SolutionFit`.

Округление на каждом шаге цепочки потерь (инвертор → DC → холостой ход →
глубина разряда) накапливает ошибку и делает результат зависимым от порядка
операций — то есть golden-тесты, посчитанные руками, начинают расходиться
с кодом на единицы Вт·ч без всякой содержательной причины.

Цена альтернативы «не округлять вообще»: в API уезжает `412.6666666666667`,
и задачу представления числа приходится решать каждому клиенту заново —
сайту и боту по-разному.

## ADR-009. Тариф сети — обязательный параметр без дефолта

`grid_tariff_uah_per_kwh` не имеет значения по умолчанию ни в ядре, ни в UI.
Тариф — не физическая константа, а региональная и коммерческая переменная
(разные области, разные группы потребления, тариф меняется). Подставить
"среднюю по Украине" цифру от имени пользователя — значит выдать чужое
предположение за его расчёт. Пользователь вводит своё значение сам.

## ADR-010. Окупаемость — в кВт·ч, не в месяцах

`payback_energy_kwh`, а не `payback_months`. Причина: у проекта нет
обоснованной цифры "типовое число отключений в месяц" — она разная для
графика 2/2, 4/4 или отдельных аварийных отключений, и любое число было бы
угадыванием. кВт·ч не требует этого допущения: чем больше энергии решение
реально отдаёт, тем ближе окупаемость, независимо от того, произошло это
за неделю или за год. Перевод кВт·ч в месяцы (если понадобится) — задача
слоя каталога, где уже известен профиль использования конкретного клиента.

## ADR-011. Ресурс циклов режется вдвое

`cycle_life_derating = 0.5`. Паспортные 3000 циклов у LiFePO4 получены в
лаборатории: контролируемая температура, ровный разряд, отсутствие глубоких
переразрядов. Реальная эксплуатация — жара в машине, частичные циклы,
периоды простоя — режет ресурс примерно вдвое. Число предварительное и
подлежит уточнению по мере накопления собственной статистики эксплуатации
(как и `declared_capacity_derating` в ADR-006).

## ADR-012. Два независимых числа: LCOE и точка окупаемости

`cost_per_kwh_uah` (LCOE) размазывает капекс на ВЕСЬ паспортный срок службы —
годится для сравнения решений между собой, но для повербанка или станции
почти всегда будет дороже сетевого тарифа: это не ошибка, а честный факт —
резервное питание физически не может быть дешевле стабильной сети.

`payback_energy_kwh` считается по маржинальной стоимости (топливо для
генератора, ноль для накопителя) и отвечает на другой вопрос: после скольких
реально полученных кВт·ч накопленная экономия покроет цену покупки. Для
накопителя это всегда сработает при `grid_tariff > 0` (экономия есть с первого
кВт·ч). Для генератора — не всегда: если топливный опекс дороже тарифа сети,
`payback_energy_kwh = None` и это тоже честный ответ, а не баг.

## ADR-013. Типы топлива — справочник, не домен

`core.economics` не знает про «бензин» и «дизель» — только про голое число
`fuel_rate_l_per_kwh`. Выбор типа топлива с типовым расходом как подсказка —
задача UI/справочника (тот же уровень, что и appliances.yaml из фазы 1):
UI подставляет стартовое значение в поле формы, пользователь может его
поправить под свою модель генератора, и только после этого число уходит в
ядро. Домен от смены линейки типов топлива не должен меняться ни строкой.

Для phase 1 нужно решить (не сейчас): таблица типовых `fuel_rate_l_per_kwh`
по типам топлива — бензин / дизель / газ, вероятно отдельно для инверторных
и обычных генераторов (расход отличается заметно). Цифры — из реальных
паспортов генераторов, которые пойдут в каталог, а не из общих таблиц
интернета: тот же принцип честности, что и с ADR-006 (замеры FNB24P).

## ADR-014. reference — отдельный слой, не адаптер источника

`reference/` — не то же самое, что `adapters/<name>/` из схемы источников
(Rozetka, AliExpress). Это твой собственный курируемый справочник, а не
внешние офферы, которые нормализуются и дедуплицируются. Но правило
направления зависимости то же: `reference` импортирует `core`, `core` о
`reference` не знает. `test_reference_imports_only_core_and_declared_libs`
проверяет это тем же AST-обходом, что и границу `core/`.

## ADR-015. requires_pure_sine — не для всех моторов подряд

Изначально был соблазн поставить `requires_pure_sine: true` на все приборы
с электродвигателем (по правилу "насос ×5-7" из доменных правил). Но
компрессор холодильника с электронной платой управления и универсальный
двигун поверхностного насоса — разный риск: плата может сгореть на
модифицированном синусе, простой насос — просто немного потеряет в КПД.

Флаг стоит там, где цена ошибки — поломка (холодильники, газовый котёл,
CPAP, кисневий концентратор), и снят там, где цена ошибки — просадка
эффективности (насосы, привід воріт). Это предварительная оценка по общей
практике, подлежит уточнению по мере накопления собственных данных —
как и коэффициенты в ADR-006 и ADR-011.

## ADR-016. Starlink и бойлер — несколько записей вместо одной "средней"

Первая версия справочника содержала по одной записи на Starlink и на бойлер
с усреднённой мощностью. Реальные данные показали, что усреднение здесь
не honest-approximation, а потеря критичной информации:

- **Starlink Mini** питается от повербанка с PD напрямую, без інвертора —
  это шина DC_USB, а не AC. Схлопнув Mini и Standard в одну запись на AC,
  калькулятор рекомендовал бы станцію там, где реально хватит повербанка.
- **Бойлер "підтримка t°" vs "повний нагрів"** отличаются на порядок
  (1.5-1.7 кВт·ч/добу против 4-5 кВт·ч за один цикл нагріву). Одна усреднённая
  цифра была бы неправильной в обе стороны в зависимости от сценария.
- **Starlink зимой** (з підігрівом снігу) потребляет вдвое больше — критично
  для зимнего блэкаута, и это ровно тот случай честности, которого нет у
  конкурентов.

Правило на будущее: если у прибора есть режимы или модели, отличающиеся
больше чем на ~30%, — это отдельные записи в справочнике, а не одно
"среднее" число. Усреднение оправдано только когда разброс укладывается
в погрешность самого расчёта (диверсити-фактор, ADR-003).

## ADR-017. Recommendation структурно не содержит commission_rate

Не «не показываем комиссию в UI», а поля нет в типе. `commission_rate` живёт
в `Candidate` (вход движка) и умирает внутри `engine.select_recommendations` —
в `Recommendation` оно не попадает никаким путём.

Правило «комиссия — не главный вес» можно исполнять дисциплиной или типом.
Дисциплина ломается на первом дедлайне: кто-нибудь добавит поле «просто чтобы
посортировать на фронте», и это пройдёт ревью как безобидное. Отсутствие поля
в dataclass превращает утечку комиссии к клиенту в ошибку `mypy`, а не в
вопрос внимательности. Зафиксировано тестом
`test_recommendation_never_exposes_commission`.

Цена: внутренняя аналитика по комиссии не может брать её из клиентского
ответа. Она берёт её по `offer_id` из `CatalogOffer` — в том слое, где это
уместно.

## ADR-018. Ранжирование — лексикографический кортеж, не взвешенная сумма

```python
key = (0 if fit.can_cover_window else 1, cost_metric, -candidate.commission_rate)
```

Взвешенная сумма (`w1*покрытие + w2*цена + w3*комиссия`) означает, что
достаточно большая комиссия арифметически компенсирует худшее покрытие.
Веса подбираются, и однажды они будут подобраны в пользу выручки — не злым
умыслом, а потому что «показатели просели». Лексикографический порядок делает
это невозможным: комиссия вообще не участвует в сравнении, пока не совпали
оба предыдущих ключа. Зафиксировано тестами
`test_commission_never_overrides_primary_ranking` и
`test_commission_breaks_ties_only`.

Цена: нет плавных компромиссов. Решение, покрывающее окно на 99%, встанет
ниже любого, покрывающего на 100%, даже будучи вдвое дешевле. Это осознанно —
см. ADR-003 про несимметричность ошибки занижения.

## ADR-019. Не прошедший жёсткий фильтр кандидат исчезает, а не показывается с предупреждением

`if not fit.can_run: continue`. Кандидат с непустым списком `blockers`
не попадает в выдачу вообще.

`FitBlocker` — это физические невозможности, а не предпочтения: слабый
инвертор, модифицированный синус под холодильник с электронной платой,
медленное переключение под газовый котёл. Показать такую позицию с плашкой
«не рекомендуется» — значит предложить купить то, что сломает прибор
пользователя. Мягкие сомнения выражаются флагами (`FitFlag`), а не блокерами:
это разные механизмы, и смешивать их нельзя.

Цена: пустая выдача — валидный ответ (`test_empty_when_nothing_fits`).

Открытый вопрос для фазы API: сейчас движок не возвращает отфильтрованных
кандидатов вместе с их `blockers`, поэтому объяснить пользователю «почему
пусто» API-слою нечем. Решается на этапе внутреннего API — либо вторым полем
в ответе движка, либо отдельным диагностическим вызовом.

## ADR-020. products и offers разделены с первого дня, при единственном источнике

Соблазн был: пока источник один (ручной YAML), держать одну плоскую таблицу
и разделить, когда появится AliExpress.

Цена этого решения — не «одна лишняя миграция потом». Она в том, что
разделение пришлось бы делать ровно в тот момент, когда добавляется первый
адаптер: миграция данных + переписывание загрузчика + переписывание
`build_candidates` + правка всех тестов каталога одновременно с отладкой
незнакомого внешнего API. Самая рискованная задача фазы 2 удвоилась бы
в объёме. Сейчас разделение стоит одного лишнего dataclass на 15 строк.

Содержательное обоснование: у физики товара и у цены разные жизненные циклы.
Цена меняется ежедневно и у каждого продавца своя, спецификация не меняется
никогда. Разные жизненные циклы — разные сущности.

## ADR-021. catalog зависит от matching, а не наоборот

`build_candidates` живёт в `catalog/candidates.py`, а не как метод
`Candidate.from_offer` в `matching/`.

Движок обязан работать на кандидатах, собранных откуда угодно: из YAML,
из будущей БД, руками в тесте. Если бы `matching` импортировал
`CatalogOffer`, удаление слоя каталога ломало бы движок, и правило проекта
(«удаление источника = удаление одной папки») перестало бы выполняться.
Граница проверяется автотестом: `MATCHING_ALLOWED = stdlib | core | matching`,
`CATALOG_ALLOWED` включает `matching` — асимметрия зафиксирована в коде теста,
а не в договорённости.

`build_candidates` при этом не полагается молча на то, что загрузчик уже
проверил ссылочную целостность, и проверяет её сам — чтобы оставаться
корректной функцией, а не корректной только в одном сценарии вызова.

## ADR-022. InverterSpec и BatterySpec — отдельные типы, а не SolutionSpec с дырами

Инвертор без АКБ не имеет ёмкости. АКБ без инвертора не отдаёт AC. Ни то,
ни другое поодиночке не может питать нагрузку, и `core.fit` оценить их
не может.

Если положить их в `SolutionSpec`, пришлось бы ослабить `__post_init__` —
сделать `capacity_wh` опциональной для всех видов решений. Тогда станция
без ёмкости, попавшая в YAML по опечатке, тоже прошла бы валидацию.
Отдельные типы позволяют `core.SolutionSpec` остаться строгим: он существует
только для того, что реально способно питать нагрузку. Полноценный
`SolutionSpec` появляется лишь после `assemble_solution` совместимой пары.

Цена: нужны функция сборки и отдельный билдер кандидатов (~80 строк).
Дешевле, чем размытые инварианты в ядре.

## ADR-023. Совместимость — по классу напряжения с допуском 15%, а не по числу

LiFePO4 на 4 ячейки — это 12.8 В, а продаётся как «12V». 16 ячеек — 51.2 В,
продаётся как «48V». Сравнение `inverter.voltage == battery.voltage`
отбросило бы почти все реально совместимые пары рынка. Фактическое
расхождение — 6.7%, допуск взят 15% с запасом.

Единственный жёсткий фильтр совместимости — класс напряжения. Протокол связи
BMS (CAN/RS485) между конкретными моделями калькулятор не проверяет: данных
на это в каталоге нет, а проверять по выдуманной таблице совместимости —
прямое нарушение принципа «только реальные данные».

Цена: часть выданных пар может не подружиться по связи BMS. Это не скрывается,
а должно быть проговорено текстом в карточке кита — ответственность за
согласование связи лежит на продавце/монтажнике, и пользователь должен
об этом знать до покупки.

## ADR-024. Комиссия кита — средневзвешенная по цене

```python
combined = (p_inv * c_inv + p_bat * c_bat) / (p_inv + p_bat)
```

Кит — не товар, а две отдельные покупки, возможно у разных продавцов
с разными ставками. Взять ставку инвертора — исказить в пользу более дорогой
половины. Взять максимум — завысить. Средневзвешенное по цене равно
фактической суммарной выручке как доле от общего чека, то есть ровно тому
числу, которое имеет смысл в разрыве ничьей (ADR-018).

Следствие: `in_stock` кита — конъюнкция обеих половин. Пропала любая — кита
в выдаче нет. Полукит показывать нельзя: он не питает нагрузку.

## ADR-025. depth_of_discharge_override — даташит товара бьёт дефолт химии

Тот же паттерн, что `measured_wh` против `capacity_wh` в ADR-006: конкретное
знание о конкретном товаре важнее классового усреднения, и факт применения
override виден во флагах (`USED_PRODUCT_DOD_OVERRIDE`), а не растворяется
в числе.

`policy.dod_for(LIFEPO4) = 0.90` — усреднение по классу. У конкретного
LiFePO4 с паспортными 80% DoD при 6000 циклов класс врёт в опасную сторону:
калькулятор пообещает энергию, которую производитель разряжать не разрешает.

Цена альтернативы «поправить policy»: глобальная константа меняется ради
одной позиции и ломает расчёт всех остальных.
Цена альтернативы «завести химию `LIFEPO4_80`»: комбинаторный взрыв энумов —
на каждое сочетание химии и паспортного DoD по значению.

Override живёт и в `SolutionSpec`, и в `BatterySpec` — и `assemble_solution`
переносит его из АКБ в собранный кит: иначе кит терял бы паспортное значение
и откатывался к классовому дефолту.

## ADR-026. Сдвиг колонок в исходной таблице инверторов

В исходном CSV значения `continuous_power_w` лежали в колонке `peak_power_w`,
а значения `peak_power_w` — в `dc_output_power_w`. Ошибка поймана сверкой
текстовых описаний позиций с числами построчно, а не просмотром таблицы
глазами.

Правило, которое из этого следует: любое число, попадающее в каталог,
сверяется с независимым источником (страница производителя или продавца)
построчно. Совпадение списка имён файлов или беглый взгляд на таблицу
не считаются проверкой.

Три позиции (Deye SUN-5K, Solarverse, LuxPower) стоят с `peak = continuous` —
это явная ЗАГЛУШКА, помеченная комментарием в `components.yaml`. Она занижает
возможности инвертора: такой кит не попадёт в выдачу там, где реально потянул
бы пусковой ток. Ошибка в безопасную сторону допустима как временная,
обратная — нет.

## ADR-027. fuel_rate_source живёт в каталоге, а не в ядре

`FuelRateSource` (`rated_specific` / `derived_from_tank` / `measured`) —
поле `CatalogProduct`, а не `SolutionSpec`.

Ядру для расчёта нужно число, а не степень доверия к нему: физика не меняется
от того, откуда взят расход топлива. А куратор данных и UI обязаны видеть
разницу — `derived_from_tank` даёт погрешность до 30-40%, и показывать его
наравне с `measured` — то же самое, что показывать паспортную ёмкость как
измеренную (ADR-006).

Тот же принцип границы, что в ADR-013: домен знает про число
`fuel_rate_l_per_kwh`, справочник знает про бензин, дизель и происхождение
цифры.

Цена: контекст числа живёт рядом со `spec`, а не внутри него — при чтении
кода надо помнить, что это связанная пара. Взамен ядро не обрастает
метаданными о качестве собственного входа.

## ADR-028. Валидация данных — тем же кодом, что защищает ядро

`csv_to_products_yaml.py` после генерации YAML прогоняет `load_catalog`
и `build_candidates` и падает с `SystemExit`, если хоть одна позиция
не проходит `SolutionSpec.__post_init__`. Ссылочная целостность
(`offer.product_id` существует среди `products`) проверяется в
`products_loader` в момент загрузки, а не в момент использования.

Отдельная «мягкая» проверка внутри конвертера неизбежно разъедется
с инвариантами ядра — и разъезд обнаружится не в конвертере, а в проде.
Единственный способ гарантировать, что YAML в репозитории всегда валиден
для движка, — валидировать его тем же кодом, который его потом читает.

Проверка при загрузке, а не при использовании: битая ссылка на `product_id`
должна давать понятную ошибку при старте приложения, а не невнятный 500-й
ответ где-то в глубине API через неделю.

Цена: `scripts/csv_to_products_yaml.py` не автономен — он импортирует
`catalog` и `core`. Приемлемо: `scripts/` — инструмент разработчика,
а не слой архитектуры, и правило направления зависимостей на него
не распространяется.

## ADR-029. Размерность метрики стоимости — отдельный элемент сортировочного ключа

```python
_SortKey = tuple[int, int, float, float]
key = (покрытие, размерность_метрики, значение_метрики, -комиссия)
```

`размерность_метрики`: 0 — грн/кВт·ч (экономика посчитана), 1 — грн (не
посчитана). Метрика вместе с размерностью собирается в `_cost_key()`.

**Инвариант:** значение метрики сравнивается только со значением той же
размерности. Числа в грн и в грн/кВт·ч не попадают в одно сравнение никогда.

До этого в один слот кортежа клали либо `ownership.cost_per_kwh_uah`
(порядок 3-40), либо `candidate.price_uah` (порядок 1500-65000), смотря по
тому, хватило ли данных конкретному кандидату. Практически это работало
правильно только потому, что цена всегда на три порядка больше LCOE — то
есть корректность держалась на разнице разрядов, а не на замысле. Достаточно
одной позиции с заниженным `cycle_life` или `expected_lifetime_wh`, чтобы
LCOE превысил чью-то цену, и порядок выдачи молча перевернулся бы.
Зафиксировано `test_cost_metric_never_compares_across_dimensions` —
тест падает на прежней реализации.

Отсутствие данных не даёт кандидату преимущества: без посчитанной экономики
он попадает на второй уровень размерности, то есть ниже любого кандидата
с полными данными при равном покрытии.

**Цена альтернативы «единая размерность на весь вызов»** (нет экономики хоть
у кого-то → ранжируем весь список по цене): нелокальность. Добавление одного
товара с незаполненным полем меняет порядок всех остальных, и порядок выдачи
перестаёт быть функцией свойств кандидата, становясь функцией состава списка.
Это невозможно ни объяснить пользователю, ни осмысленно протестировать.

**Заодно:** нулевой или отрицательный `grid_tariff_uah_per_kwh` и
`fuel_price_uah_per_l` теперь отвергаются на границе движка. Раньше
`OwnershipInput` бросал `InvalidOwnershipInputError`, `_build_ownership_input`
его глотал, и экономика молча не считалась ни у кого — ошибка ввода
превращалась в тихую деградацию выдачи.

## ADR-030. explain_rejections — отдельная функция, не расширение select_recommendations

```python
def explain_rejections(
    requirement: EnergyRequirement,
    candidates: Sequence[Candidate],
    policy: CalculationPolicy = DEFAULT_POLICY,
) -> tuple[RejectionReason, ...]
```

Закрывает открытый вопрос ADR-019: движок молча отбрасывал заблокированных
кандидатов, и объяснить пользователю «почему пусто» было нечем. Решение —
вариант B из трёх рассмотренных: не трогать контракт `select_recommendations`
(вариант A) и не размазывать диагностику по API-слою (вариант C), а завести
параллельную диагностическую функцию в том же модуле, что и фильтрация.

`matching` остаётся единственным местом, которое знает, что значит «не
подошёл»: и решение о включении в выдачу, и объяснение исключения растут
из одного и того же `evaluate_fit`. Контракт `select_recommendations` и все
существующие тесты не меняются ни строкой.

**Инвариант разбиения.** Каждый кандидат оказывается либо в
`select_recommendations`, либо в `explain_rejections`, никогда не в обоих
сразу и не в ни одном. Частичное покрытие окна (`can_run=True,
can_cover_window=False`) — это выдача с худшим рангом, не отказ; в
`explain_rejections` оно не попадает. Зафиксировано
`test_complements_select_recommendations_partition`.

**Инвариант независимости причин.** `out_of_stock` и `blockers` считаются
отдельно друг от друга. Кандидата без наличия `evaluate_fit` всё равно
проверяет — так же, как проверила бы select_recommendations, дойди она до
этой строчки. Смешивать причины в одно сообщение нельзя: «нет на складе» —
временное состояние, «модифицированный синус не подходит холодильнику» —
постоянное, и склеивать их значило бы прятать постоянную причину за
временной.

Экономика (`grid_tariff_uah_per_kwh`, `fuel_price_uah_per_l`) в сигнатуру
не входит: она никогда не блокирует кандидата, только сортирует прошедших
(ADR-018), так что объяснению отказа она не нужна.

Цена решения: два прохода по кандидатам в худшем случае — API вызывает
`explain_rejections` вторым запросом, только когда `select_recommendations`
вернул пусто (или по явному запросу «почему нет конкретного товара»), а не
на каждый расчёт. Для каталога в десятки-сотни позиций цена незаметна.

## Открытая проблема данных: expected_lifetime_wh у генераторов

`_build_ownership_input` для `SolutionKind.GENERATOR` требует
`expected_lifetime_wh` на оффере — у генератора нет `cycle_life`, ресурс
меряется моточасами. Сейчас поле не заполнено ни у одного из четырёх
генераторов каталога, поэтому экономика для них не считается вообще.

Следствие на реальной выдаче (холодильник + роутер + Starlink, окно 6 ч,
тариф 4.32, бензин 62 грн/л): Hyundai HHY 1050Si за 15 330 грн, полностью
закрывающий окно, стоит третьим — под станциями за 40 990 и 64 999 грн.

ADR-029 этот порядок не меняет и не должен: он делает причину явной
(`ownership is None` доезжает до клиента), но лечится проблема только
данными. Число берётся из паспортного моторесурса в часах, умноженного на
номинальную мощность, и подставлять правдоподобную оценку вместо паспорта
здесь нельзя.

## ADR-031. Диагностика отказов — второй проход, только при пустой выдаче

`POST /api/v1/recommendations` вызывает `explain_rejections` тогда и только
тогда, когда `select_recommendations` вернул пустой список. На успешном
расчёте второго прохода по каталогу нет.

В ответе `rejected` — это `list | None`, и `None` с `[]` значат разное:
`None` — диагностика не запускалась (нашлись рекомендации), `[]` —
запускалась и не нашла ни одного отклонённого. Схлопнуть их в пустой список
значило бы потерять различие между «не понадобилось» и «не нашлось».

Цена альтернативы «считать обе ветки всегда»: на каждый успешный расчёт —
лишний полный проход по каталогу с вызовом `evaluate_fit` для каждого
кандидата, при том что результат клиенту не нужен. Проще в коде на три
строки, дороже на каждом запросе.

Граница между «отказ» и «подходит хуже» проходит по `can_run`, а не по
покрытию. Кандидат, который тянет нагрузку по мощности, но не покрывает
окно по энергии, остаётся в выдаче с `can_cover_window=false` — это ответ,
а не отказ (ADR-019). Тест `test_partial_coverage_is_still_an_answer`
фиксирует именно эту границу, потому что при написании тестов API она была
нарушена с первого раза: нагрузка «40 холодильников» давала не пустую
выдачу, а выдачу с частичным покрытием.

## ADR-032. Слой api/ — внешний, и это проверяется в обе стороны

```
api/
  schemas.py           контракт: pydantic-модели запроса и ответа
  catalog_provider.py  загрузка YAML один раз (lru_cache), сборка кандидатов
  app.py               FastAPI: перевод HTTP <-> домен, больше ничего
```

Два теста границы вместо одного:

- `test_api_is_the_outermost_layer` — `api/` может импортировать `core`,
  `reference`, `matching`, `catalog`, `fastapi`, `pydantic` и ничего сверх.
- `test_inner_layers_never_import_api` — ни один внутренний слой не
  импортирует `api`. Удаление папки `api/` целиком не ломает домен.

Односторонней проверки здесь мало: для внутренних слоёв запрет выражается
тем, что `api` не входит в их whitelist, но у внешнего слоя такого механизма
нет — его whitelist самый широкий. Обратное правило приходится писать явно.

`app.py` не содержит ни одного решения о подборе: только перевод кодов
приборов в `LoadProfile`, вызов движка и сборка ответа. Появление здесь
условия вида «а для генераторов посчитаем иначе» — признак, что условию
место в `matching`.

Доменные enum'ы (`FitBlocker`, `FitFlag`) уходят в схемы напрямую, а не
дублируются строковыми константами: pydantic сериализует их по `.value`.
Дублирование означало бы, что при добавлении нового блокера в ядро API
молча отдаёт устаревший набор.

`catalog_provider` — единственное место во всём проекте, которое знает про
путь к `data/`. Когда в фазе 2 появится PostgreSQL, меняется тело
`load_all_candidates`; схемы, обработчик и движок не трогаются.

## ADR-033. tracking/ — отдельный слой-лист, не часть домена и не часть API

```
tracking/
  click.py       Click: offer_id, source, scenario_hash, position, click_id, время
  port.py        ClickLog — Protocol. Только record и count
  sqlite_log.py  адаптер SQLite
  sub_id.py      сборка sub_id для партнёрской ссылки
```

`tracking/` импортирует только stdlib — проверяется
`test_tracking_is_a_leaf_layer`. Клик не знает про ватт-часы, а расчёт не
знает про клики; единственная связь между ними — строка `offer_id`.

`click_id` генерируется в приложении, а не автоинкрементом базы: он уходит
в `sub_id` партнёрской ссылки ДО записи. Ждать идентификатора от базы
значило бы поставить формирование ссылки в зависимость от успеха вставки.

В порту нет `update` и `delete`, и это инвариант, а не недоделка. Журнал
атрибуции, который можно править, бесполезен как аргумент в споре с
CPA-сетью о неоплаченном заказе.

SQLite, а не PostgreSQL: критерий перехода в фазу 2 — «~100 расчётов и
заметный CTR». Сотня строк append-only не нуждается ни в сервере, ни в
миграциях. Замена — новый класс на том же порту и одна строка в `app.py`.

## ADR-034. Журнал кликов передаётся в роутер снаружи

`api/redirect.py` экспортирует не готовый роутер, а `build_router(click_log)`.
Конкретная реализация выбирается один раз в `app.py` — это композиционный
корень.

Альтернатива «импортировать SqliteClickLog прямо в обработчике» короче на
две строки и делает порт `ClickLog` декоративным: подменить журнал в тесте
можно было бы только monkeypatch'ем модуля. Сейчас тест подставляет
`MemoryClickLog` как обычный аргумент, и это та же проверка порта, что
и продакшен-путь.

Порядок операций в обработчике жёсткий: сначала `record`, затем 302.
Обратный порядок физически невозможен — после редиректа обработчик не
выполняется. Если запись упала, пользователь получает 500 и мы об этом
узнаём. Молча увести человека на маркетплейс, потеряв атрибуцию, хуже:
комиссию за такой переход никто не заплатит, а факт перехода не сохранится.

Оффер без URL даёт 404, а клик НЕ записывается. Записать клик и никуда не
увести — значит завысить CTR на мёртвых ссылках и испортить ровно ту
метрику, ради которой редирект и заводится.

## ADR-035. Кит не имеет одной целевой страницы

`kit__inv_X__bat_Y` в индекс редиректов не попадает. Кит — это две покупки
у (возможно) разных продавцов, и одного URL у него нет. `/go` для кита
отдаёт 404.

Следствие для UI: карточка кита показывает ДВЕ кнопки перехода, по одной на
компонент, и каждая идёт через свой `/go/{component_offer_id}`. Это не
обходной путь, а честное отражение того, что человеку предстоит оформить
два заказа.

Из-за этого в `ComponentOffer` добавлено поле `url` — раньше его не было,
потому что до появления редиректа компонент никуда не вёл.

**Открытая проблема:** `Recommendation` содержит только составной
`offer_id` кита и не отдаёт идентификаторы двух его половин. Клиент не может
построить эти две ссылки из ответа API. Решается расширением
`Recommendation` (поле с составляющими офферами) — до этого карточки китов
кликабельными не будут.

## Открытая проблема данных: URL офферов

Ни у одного из 28 офферов каталога (13 товарных + 15 компонентных) не
заполнено поле `url`. Редирект `/go` работает и покрыт тестами, но в
продакшене отдаёт 404 на любой оффер, потому что вести некуда.

Заполняется вручную, ссылками на страницы продавцов. До подписания
CPA-договоров это обычные ссылки на Rozetka/Prom — клик всё равно
логируется, и метрика CTR фазы 1 набирается ещё до появления партнёрских
программ. Когда договоры появятся, меняется только содержимое поля `url`
и, возможно, имя параметра `SUB_ID_PARAM`.

## ADR-036. Двойная защита от индексации /go

`X-Robots-Tag: noindex, nofollow` в самом ответе редиректа + `Disallow: /go/`
в `robots.txt`. Одного `robots.txt` мало: краулер может знать о ссылке из
внешнего источника (её кто-то запостил, она попала в чей-то сайтмап) раньше,
чем прочитал правило Disallow, и один заход посчитает страницу. Заголовок —
подстраховка на этот случай, он действует независимо от того, читал ли
краулер `robots.txt` вообще.

Партнёрские ссылки в индексе — риск санкций и от Google, и от самих
CPA-сетей (Rozetka размечает такие требования отдельно). `rel="sponsored"`
на карточках со стороны фронтенда — тот же принцип, но это уже разметка,
не API; делается на этапе страницы (`/rozrakhunok-avtonomii`).

## ADR-037. component_offer_ids — поле, а не парсинг offer_id

`Candidate.component_offer_ids: tuple[str, ...] | None` заполняется там же,
где собирается составной `offer_id` кита (`catalog/kit_candidates.py`), и
переносится через движок в `Recommendation`, а затем в `RecommendationOut`
без изменений.

Альтернатива — распарсить `"kit__inv_x__bat_y"` в API-слое по разделителю
`__` — работала бы сегодня, но привязывала бы клиента к внутреннему формату
строки, которая принадлежит `catalog` (ADR-020, ADR-021) и может измениться
без предупреждения: например, если component_id инвертора или АКБ когда-то
сам будет содержать `__`. Поле — контракт, формат строки — деталь реализации.

**Инвариант:** `None` означает «один переход» — простой товар, ведёт по
собственному `offer_id`. Не-`None` означает «несколько переходов» — кортеж
из ≥2 частей, каждая часть — рабочий `offer_id` для отдельного `/go`.
Кортеж из одного элемента запрещён `Candidate.__post_init__` — если частей
меньше двух, это не составной продукт и полю нечего в нём делать; такое
состояние — ошибка сборки кандидата, а не осмысленный кит из одной покупки.

Резолвер редиректа (`api/redirect_targets.py`) не менялся: индекс строился
из `offer_id` товарных и компонентных офферов с самого начала, а составной
`"kit__X__Y"` в него никогда не попадал — часть путаницы, которую я сам
внёс в ADR-035, была мнимой: коллизии искать было негде.

Закрывает открытую проблему из ADR-035: карточка кита теперь может
отрисовать две кнопки перехода, по одной на `component_offer_ids[0]` и
`component_offer_ids[1]`, каждая ведёт через свой `/go/{offer_id}`.

## ADR-038. Display-контракт — отдельный индекс в api/, Recommendation не расширяется

**Проблема.** `RecommendationOut` несёт данные для решения (offer_id, price_uah,
fit, ownership, component_offer_ids), но не данные для карточки (имя, бренд,
картинка, продавец). Эти данные есть в catalog/ (`CatalogProduct`,
`CatalogInverter`, `CatalogBattery`, `CatalogOffer`, `ComponentOffer`), но
`matching.Recommendation` их не несёт и не должен — движок ранжирования не
принимает решений по бренду или картинке, и любая связь между matching/ и
витриной означала бы, что правка каталога заставляет менять ранжирование
(нарушение ADR-021: catalog зависит от matching, не наоборот).

**Решение.** Склейка происходит в api/, в новом модуле `api/display_index.py`,
а не в catalog/ и не расширением `Candidate`/`Recommendation`. Это чистая
HTTP-склейка каталожных данных по offer_id — то, для чего api/ и существует
(единственный слой, которому разрешено знать все остальные).

```python
class DisplayIndex:
    def get(self, offer_id: str) -> DisplayEntry: ...  # KeyError на неизвестном offer_id

def build_display_index(...) -> DisplayIndex: ...
```

Строится один раз через `lru_cache`, рядом с существующим единственным местом,
знающим путь `data/` (`catalog_provider.py`), не пересобирается на каждый запрос.

**Новые/изменённые поля каталога** (реализация — S3, не эта сессия):

| Где | Поле | Обоснование |
|---|---|---|
| `catalog/components.py` | `CatalogInverter.image`, `CatalogBattery.image: str \| None = None` | Повтор уже существующего `CatalogProduct.image`, не новый паттерн |
| `catalog/products.py` | `class CapacitySource(Enum): RATED / THIRD_PARTY / MEASURED` | Тот же паттерн, что `FuelRateSource` (ADR-013/027) — provenance числа, не физика |
| `catalog/products.py` | `CatalogProduct.capacity_source`, аналогично `CatalogBattery.capacity_source: CapacitySource \| None` | Живёт рядом со spec, не внутри `SolutionSpec`/`BatterySpec` — честность замера не меняет физику расчёта |
| `data/sources.yaml` | `{domain: seller_label}` | Единый источник отображаемого имени продавца (поле — `seller_label`). `CatalogOffer.source`/`ComponentOffer.source` остаются техническим доменом — не переименовываются, чтобы не смешаться с будущей сущностью CPA-сети (отдельный ADR до логики sub_id, см. ошибку №10 в списке известных) |
| `catalog/components.py` | `InverterSpec.accepts_solar_input: bool = False` | Слой `core/` этим ADR не затрагивается вообще: `InverterSpec` — каталожный тип, а не доменный (ADR-022). Это физический факт о железе (инвертор гибридный), а не витринный текст — переиспользуется в F2-1 (модель притока энергии), не задел впустую |

Отсутствие домена оффера в `sources.yaml` — ошибка загрузки, не молчаливый
fallback на сырой домен (тот же принцип, что уже применён к пустым `url`,
ошибка №4 в известных). Отсутствие картинки конкретного товара — НЕ ошибка
загрузки, `image_url: None` допустим, шаблон S4 рисует плейсхолдер: у 21 из
21 товара сейчас нет картинки, и это не должно блокировать релиз.

**Новые типы `api/schemas.py`:**

```python
class ComponentRole(str, Enum):
    PRIMARY = "primary"     # простой товар, единственная покупка
    INVERTER = "inverter"   # кит, элемент 0 component_offer_ids
    BATTERY = "battery"     # кит, элемент 1 component_offer_ids

class PurchaseOut(BaseModel):
    offer_id: str
    role: ComponentRole
    name: str
    brand: str
    image_url: str | None
    seller_label: str
    price_uah: float
```

`RecommendationOut` дополняется:

```python
purchases: tuple[PurchaseOut, ...]        # len==1 простой товар, len==2 кит — инвариант, не Optional
capacity_source: CapacitySource | None    # None = генератор, ёмкости нет
solar_optional: bool | None               # True только у кита с гибридным инвертором
```

`price_uah` на верхнем уровне `RecommendationOut` не удаляется — остаётся
суммой (уже считается для китов в `kit_candidates.py`), нужен для сортировки
и заголовка без обхода `purchases`.

Роль в ките назначается по **позиции** в `component_offer_ids`
(`purchases[0]` = INVERTER, `purchases[1]` = BATTERY) — фиксированный порядок
уже задан в `kit_candidates.py:50`. Парсинг строки offer_id по-прежнему
запрещён (правило из `matching/candidate.py`).

**Что НЕ входит в контракт:**

- рейтинги/отзывы — нет источника данных;
- остаток на складе числом — только `in_stock: bool`;
- CPA-сеть / sub_id — `seller_label` это витрина, не платящая сторона;
- совместимость кабеля — `CatalogAccessory`, Фаза 2, не `Solution`;
- выработка солнечных панелей — `accepts_solar_input` только факт о железе, модель притока энергии целиком в F2-1;
- мультивалютность — только ₴.

**Альтернативы, отклонённые явно:**

- Расширить `Candidate`/`Recommendation` display-полями напрямую — отклонено:
  заставило бы `matching/` знать о брендах и картинках, что нарушает
  направление зависимостей и требование "движок работает на кандидатах,
  собранных откуда угодно" (ADR-021).
- Хранить `image_url` внешней ссылкой на сайт продавца (hotlink) — отклонено
  как продуктовое решение, не как часть этого контракта: referrer-блокировка,
  отсутствие контроля над исчезновением файла у продавца, нарушение принципа
  "маркетплейсы — только через ночной ETL". Own-hosted изображения —
  отдельная задача данных, S8, не блокирует этот ADR.
