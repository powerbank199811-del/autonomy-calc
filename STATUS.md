### Что реализовано

**ADR-039 (партиционирование).** `select_recommendations` группирует
прошедших фильтры кандидатов по `SolutionKind`, внутри типа применяет
существующий `_cost_key` без изменений (ADR-018/029 подтверждены),
берёт до `limit_per_kind` на тип, сливает обратно в плоский список
и сортирует глобально тем же ключом. Группировка для показа —
обязанность `api/`, в этой сессии НЕ реализована (в бриф не входила,
шаблон не трогали).

**ADR-041 (граница Парето).** `matching/pareto.py`, две функции:
`pareto_frontier(others, face)` и `compress_frontier(frontier)`.
Правило доминирования — решение владельца, зафиксировано:
B доминирует A, если `price(B) <= price(A)` И `hours(B) >= hours(A)`,
И хотя бы одно неравенство строгое. Требование строгости обязательно:
без него два кандидата с одинаковыми ценой и часами доминировали бы
друг друга взаимно и оба исчезли бы из выдачи. Отдельного tie-break
НЕТ сознательно — критерий выбора «кого из двух равных оставить»
не из чего вывести, это тот же класс ошибки, за который отвергли
порог 75% в ADR-039 и взвешенную сумму в ADR-041.

**Лицо типа вне Парето-пула.** Первый по `_cost_key` внутри типа
входит в выдачу безусловно, Парето применяется только к остальным,
но лицо участвует как доминатор. Это прочтение дословного текста
ADR-041 («исключается из списка остальные варианты») и п.4 брифа
(«лицо типа — первый по `_cost_key`, не самый дешёвый»). Без этого
разделения Парето по сырой цене выталкивал бы из выдачи кандидата
с лучшим LCOE — прямое нарушение гарантии ADR-029, поймано тестом
`test_cost_metric_never_compares_across_dimensions` до написания кода.

**Контракт.** `Recommendation.kind: SolutionKind` (доменный факт,
не display — ADR-038 не нарушен). `RecommendationOut.kind` — одно
новое поле, сверх него схема не расширялась. `limit` → `limit_per_kind`,
дефолт 5 → 3 (при 4 типах старое число дало бы вчетверо больше карточек).

**Текст при пустой выдаче.** `summarize_rejections(rejections, window_hours)`
— второй параметр добавлен, вызов в `api/app.py` передаёт
`response.requirement.window_hours`. Ветка срабатывает для кандидата
с `blockers=()` и `out_of_stock=False` — того самого случая
can_run=True / can_cover_window=False, у которого причины отказа
в терминах `core/fit.py` нет. Текст: «жодне рішення не витримує
{N} годин — спробуйте менший час або приберіть потужні прилади».
НЕ костыль: когда появится FitBlocker в `core/`, ветка останется
fallback'ом для любого блокера без текста. Логика причины
в `api/` не дублируется — только текст.

(cycle_life → dimension) закрыт партиционированием структурно
